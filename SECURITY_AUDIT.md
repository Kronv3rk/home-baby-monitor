# Аудит протокола сопряжения HomeBabyMonitor

**8 ноября 2026 года.** Рассмотрены исходники 0.4.4 и исправления для 0.4.5. Метод: ручная проверка криптографической схемы, модели угроз и сетевых путей, интеграционные негативные тесты. Это внутренний аудит кода, **не независимая криптографическая экспертиза и не формальное доказательство безопасности**.

## Границы

Проверены `SecureSignalCipher.kt`, `PairingLink.kt`, `WireProtocol.kt`, `SignalPipe.kt`, `BabySignalServer.kt`, `ParentConnector.kt`, `PinRateLimiter.kt` и сетевые вызовы `MonitorService.kt`. Модель атакующего: постороннее устройство в той же Wi-Fi-сети, способное перехватывать, задерживать, менять или повторять пакеты, и отдельный сценарий, когда QR-код был сфотографирован. Компрометация самой ОС Android, аппаратного генератора случайных чисел и устройств находится вне охвата.

## Механизм

1. Камера генерирует случайный код из 20 символов алфавита из 32 знаков: **100 бит энтропии** при исправном `SecureRandom`. Код переносится вручную или QR-кодом вместе с частным IP-адресом.
2. Клиент и сервер открыто обмениваются двумя новыми 128-битными случайными значениями `HELLO` и `CHALLENGE`.
3. Из SHA-256 от кода с меткой протокола и HMAC-SHA256 от двух случайных значений выводятся разные AES-256 ключи для двух направлений. Обмен `AUTH`/`OK` подтверждает владение кодом. Новый отказ `BUSY` также шифруется.
4. Последующая сигнализация (SDP/ICE) защищена AES-GCM с 128-битным тегом, раздельными возрастающими счётчиками nonce и AAD с контекстом соединения. Медиа WebRTC защищает собственным DTLS-SRTP.

Эффективная стойкость к подбору определяется прежде всего энтропией кода (около **100 бит**), а не только размером AES-ключа. Уменьшать код до шести цифр при такой схеме нельзя.

## Подтверждённые находки

| Уровень | Проблема | Исправление / проверка |
|---|---|---|
| Средний | Один неавторизованный клиент удерживал TCP-соединение и блокировал других | Регрессионный тест сначала упал; сервер переведён на ограниченный пул из 4 обработчиков с очередью 8 |
| Средний | Неудачные попытки с одного IP блокировали сопряжение для всех | Ограничение попыток сделано отдельным для каждого IP; после успешного входа накопленные ошибки сбрасываются |
| Повышенный при утечке QR | Устройство с копией кода могло бесшумно заменить уже подключённого родителя с другого IP | Тест воспроизвёл перехват; при активном сеансе сервер возвращает зашифрованное `BUSY` для другого адреса |

Тестовые сценарии включены в `tools/ServerIntegrationSmokeTest.kt`; GitHub Actions запускает `tools/verify-jvm.sh` перед сборкой. Ограничения пула только снижают вероятность DoS — многоузловой злоумышленник способен перегрузить локальную сеть.

## Что в схеме сделано правильно

- Код не посылается в открытом виде по TCP; он выводится на экран устройства.
- Проверка владения кодом связана с двумя случайными значениями конкретного соединения.
- Ключи для двух направлений разные, а счётчики nonce возрастают.
- Подмена зашифрованного сообщения или повтор ранее принятого пакета приводят к отказу в проверке AES-GCM.
- Неверный код не даёт доступа к параметрам WebRTC. SDP, включая отпечатки DTLS, передаётся через аутентифицированный сигнальный канал.
- Сервер слушает локальный Wi-Fi IPv4, а не все интерфейсы Android.

Это свойства изученной реализации и конкретных тестов, а **не гарантия отсутствия других уязвимостей**.

## Оставшиеся риски

**Нет forward secrecy у сигнального TCP-канала — средний риск.** Ключи сеанса определяются кодом и открытыми случайными значениями. Если злоумышленник записал соединение и позже получил код, он сможет расшифровать старую *сигнализацию*. Это само по себе не раскрывает прежние DTLS-SRTP медиа-ключи WebRTC, которые согласуются отдельно.

**Нет криптографической идентичности доверенного родительского телефона.** Код — общий секрет. После отключения текущего родителя любое устройство с действительным кодом может снова подключиться. Сравнение IP не заменяет проверку публичного ключа устройства. Нужны отзыв доверия и явное подтверждение нового родителя.

**QR-код доступен на экране камеры во время сопряжения.** Его фотографирование раскрывает секрет. Требуются срок действия кода, отзыв и обновление ключа по действию пользователя.

**Самостоятельная схема согласования ключей не имеет формальной проверки.** Использование SHA-256/HMAC/AES-GCM по отдельности не превращает весь протокол в стандартный TLS или Noise. Быстрый KDF допустим здесь только благодаря случайному 100-битному секрету; для короткого PIN потребуется PAKE.

**Доступность на недоверенной LAN ограничена.** UDP-объявления не аутентифицированы; допускают подделку и срыв поиска. TCP-пул конечен. Android `usesCleartextTraffic=false` не шифрует самостоятельно открытые TCP-сокеты.

## План устранения рисков

Для стабильной версии заменить собственную процедуру вывода ключей на стандартизованный обмен с эфемерными ключами и обязательной проверкой идентичности устройства (например, TLS 1.3 с привязкой к публичному ключу, переданному через QR). Для коротких кодов использовать проверенный PAKE, например SPAKE2+. После первого подключения хранить разрешённый публичный ключ родителя, предусмотреть отзыв устройств и ограничение времени жизни кода. Затем провести стороннюю экспертизу и испытания на настоящих телефонах.

Основания для сравнения: [OWASP MASVS-NETWORK](https://mas.owasp.org/MASVS/08-MASVS-NETWORK/), [RFC 5869 (HKDF)](https://www.rfc-editor.org/rfc/rfc5869), [RFC 9383 (SPAKE2+)](https://www.rfc-editor.org/rfc/rfc9383).

**Итог:** в проверенных сценариях не найден способ прочесть сигнализацию без знания кода, но это не доказательство конфиденциальности. Подтверждены и исправлены три проблемы с доступностью и контролем подключений. Схема остаётся прототипом, не пригодным как единственная система наблюдения за ребёнком.
